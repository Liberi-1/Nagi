# Nagi v0.2 开发日志

## 1. 版本概述

v0.2 的目标是在保持 v0.1 语音对话闭环和 Unity 客户端可用的前提下，为 Nagi 增加数据持久化、短期多轮上下文和 Web 管理能力。

本版本没有重写实时链路，而是将数据层逐步接入既有 Pipeline：

```text
Unity 语音输入
→ Whisper ASR
→ MySQL 用户与启用人设
→ Redis / MySQL 最近对话历史
→ DeepSeek LLM
→ MySQL 保存本轮对话
→ Redis 追加本轮缓存
→ Edge TTS
→ Unity 播放语音并切换动画
```

同时新增独立的管理链路：

```text
Vue 管理后台
→ FastAPI
→ MySQL 人设、日志与统计
→ Edge TTS 音色试听
```

当前状态：核心功能、专项验收、前后端全量回归和文档同步均已完成，准备合并到 dev 并创建 v0.2 标签。

## 2. 本版本目标

1. 使用 MySQL 保存用户、人设和完整对话记录。
2. 使用 Redis 缓存同一连接最近 N 轮上下文。
3. 让 LLM 支持同一 WebSocket 连接内的多轮对话。
4. 使用 FastAPI 提供人设、日志、统计和试听接口。
5. 使用 Vue 管理后台支持人设编辑、日志分页筛选、TTS 试听和情绪统计。
6. 尽量保持 v0.1 Pipeline、WebSocket 协议和 Unity 客户端可用。
7. Redis 不可用时能够回退 MySQL，不阻断语音主流程。

## 3. 技术选型

| 方向 | 选择 | 原因 |
| --- | --- | --- |
| 数据库 | MySQL 8 | 结构化持久化、查询筛选和分组统计 |
| ORM | SQLAlchemy 2 | 将数据访问集中在 Repository，减少重复 SQL |
| MySQL 驱动 | PyMySQL | 与当前 Python 后端集成简单 |
| 缓存 | Redis List | 适合按顺序追加、读取和裁剪最近 N 轮 |
| Windows Redis 方案 | Memurai Developer | 兼容 Redis 协议，不为 v0.2 提前引入 Docker |
| 管理接口 | FastAPI | 参数校验、类型提示和接口结构清晰 |
| 管理前端 | Vue 3 + TypeScript + Vite | 适合单页管理后台，保持项目轻量 |
| 路由 | Vue Router + Hash History | 本地静态预览不需要服务器路由重写 |
| 实时通信 | 保留 WebSocket 协议 | 避免重写 Unity 客户端 |
| LLM | DeepSeek OpenAI 兼容接口 | 延续 v0.1 接入方式 |
| ASR / TTS | Whisper base CPU / Edge TTS | 保持既有语音闭环 |

## 5. 数据层设计

### 5.1 三表结构

`users` 保存本地用户。

`personas` 保存用户人设，包括名称、内容、启用状态和更新时间。

`conversation_records` 一行保存一轮完整对话：

```text
user_id
persona_id
session_id
request_id
user_text
assistant_text
emotion
created_at
```

一轮不是一条单独消息，而是：

```text
一条用户输入 + 一条角色回复
```

这种结构与 Redis 缓存项和 LLM 历史展开方式保持一致。

### 5.2 为什么 MySQL 是权威数据源

MySQL 保存完整历史，不受最近 10 轮裁剪影响。

Redis 只用于减少重复查询，不能成为唯一的数据来源。出现以下情况时都可以从 MySQL 恢复：

- Redis 未命中；
- 缓存内容损坏；
- Redis 服务不可用；
- 缓存写入失败；
- Redis 重启或数据过期。

因此缓存故障不应该等价于对话永久丢失。

### 5.3 人设来源变化

v0.1 直接从 `backend/config/persona.md` 读取人设。

v0.2 改为：

- 首次初始化时，从文件导入数据库；
- 后续运行以 MySQL 中启用人设为准；
- 管理后台修改数据库人设；
- Pipeline 每轮重新读取当前启用人设；
- 直接修改文件不会覆盖数据库中已有的人设。

这避免了文件和数据库同时作为权威来源而产生不一致。

## 6. 多轮上下文设计

### 6.1 会话标识

每个 WebSocket 连接建立时生成独立 UUID：

```text
session_id = uuid.uuid4().hex
```

同一连接中的所有请求共享该 ID。

`request_id` 仍用于配对请求和响应，但不用于查询历史。两者职责不同：

| 字段 | 用途 |
| --- | --- |
| `session_id` | 隔离会话、查询上下文 |
| `request_id` | 配对单次请求与响应 |

### 6.2 发送给 LLM 的消息

消息顺序为：

```text
system：当前数据库人设
历史 user / assistant 消息
当前 user 输入
```

历史记录不能注入额外的 `system`，当前用户输入必须放在最后。

### 6.3 最近 10 轮滑动窗口

默认：

```python
DEFAULT_CONTEXT_TURNS = 10
```

达到 10 轮后，每增加一轮就淘汰最旧的一轮：

```text
第 11 轮请求：历史为第 1～10 轮
第 12 轮请求：历史为第 2～11 轮
第 13 轮请求：历史为第 3～12 轮
```

MySQL 中的完整记录不会随之删除。

### 6.4 重连边界

v0.2 没有实现跨连接会话恢复：

- 重连会生成新 `session_id`；
- 新会话历史从 0 轮开始；
- 旧会话仍保留在 MySQL 和网页日志中；
- 旧 Redis 缓存不会自动并入新会话。

跨重连恢复最近会话计划放到 v0.3。

## 7. Redis 缓存设计

缓存键：

```text
nagi:context:{user_id}:{session_id}
```

每项是一轮 JSON：

```json
{
  "user_text": "用户输入",
  "assistant_text": "角色回复"
}
```

操作方式：

- `RPUSH` 追加新对话；
- `LRANGE key -N -1` 读取最近 N 轮；
- `LTRIM key -N -1` 保留最近 N 轮；
- `EXPIRE` 设置或续期 7 天 TTL。

### 降级流程

```text
读取 Redis
├── 命中：直接使用缓存
├── 未命中或损坏：读取 MySQL → 重建缓存
└── Redis 不可用：读取 MySQL → 继续主流程
```

如果追加失败，当前进程会记录需要重新校准的会话，避免 Redis 恢复后继续读取故障前的旧缓存。

## 9. 主要问题与修复

### 9.1 Pipeline 文件名大小写

Windows 文件名不区分大小写，因此 `Pipeline.py` 与 `pipeline.py` 的导入问题在本机可能不明显，但 Linux 会失败。

修复：统一为 `backend/pipeline.py`，避免跨平台导入差异。

### 9.2 已忽略音频仍被 Git 跟踪

`.gitignore` 只能忽略未跟踪文件，不能自动取消已经入库文件的跟踪。

修复：将测试 WAV 和临时 MP3 移出 Git 索引，同时保留本地文件。

### 9.3 MySQL 命令不存在

先区分是没有安装，还是已经安装但未加入 PATH，而不是直接修改项目代码。

最终通过 MySQL Installer 安装并启动 MySQL80，创建 `nagi` 数据库和专用账号，再验证当前用户和数据库。

### 9.4 PowerShell 中文乱码

问题并不只是显示乱码：

1. PowerShell 错误解码 UTF-8 响应；
2. 随后的 PUT 将乱码对象写回数据库；
3. 再次“恢复”时仍可能恢复乱码内容。

修复：

- FastAPI JSON 响应显式声明 `application/json; charset=utf-8`；
- 中文写回测试改用 Python UTF-8 bytes；
- 从原始 `persona.md` 重新导入正确内容；
- 不再通过 PowerShell 对象往返写中文。

### 9.5 Vite 没有继续输出

`npm run dev` 启动后是常驻开发服务器，不是卡死。保持窗口运行并打开 `localhost:5173` 即可。

`npm run build` 只负责构建，不会启动开发服务器。

### 9.6 VS Code 找不到 Vue 模块

文件路径正确，但缺少 Vite 和 Vue SFC 类型声明。

修复：增加 `src/vite-env.d.ts`，加载 `vite/client` 并声明 `*.vue` 模块。

### 9.7 ConversationsView 构建失败

空 Vue 文件没有 `template` 或 `script`，因此生产构建失败。

修复：补全页面真实内容后重新构建，而不是弱化构建脚本。

### 9.8 在 backend 执行 npm 命令

三个目录职责不同：

- `web-admin/`：npm 安装、启动和构建；
- `backend/`：FastAPI、WebSocket 和 Python 测试；
- 仓库根目录：Git 操作。

在错误目录执行 `npm run build` 会出现找不到 `package.json`，不是前端依赖本身损坏。

### 9.9 音色页面空白

原因是路由、导航或组件修改没有完整保存和注册。

修复：检查路由表、导航入口和组件路径，重新构建并强制刷新浏览器。

## 10. 关键 Bug：Redis 永远只有一轮历史

### 10.1 现象

网页日志显示：

- 用户明确说过喜欢蓝色、绿茶和寿司；
- 后续提问时 Nagi 却说没有说过；
- 但代号有时仍能回答。

最初仅凭网页截图，无法区分模型回忆不稳定和数据层异常。

### 10.2 后端日志定位

完整日志显示：

```text
MySQL：历史 0 轮
MySQL：历史 1 轮
Redis：历史 1 轮
Redis：历史 1 轮
Redis：历史 1 轮
……
```

正确结果应该是：

```text
0、1、2、3、4……
```

MySQL 每轮都保存成功，因此问题锁定在 Redis 追加或 Pipeline 调用位置，而不是完整记录丢失。

### 10.3 根因

`pipeline.py` 中追加 Redis 的代码错误地缩进到了数据库异常处理块里，而且位于 `raise` 之后：

```python
except Exception as e:
    raise StageError("DB", e)

    # 这里的代码永远不会执行
    if context_turns &gt; 0:
        append_to_cache(...)
```

结果是：

1. MySQL 每轮正常保存；
2. Redis 从不追加本轮；
3. 第二次请求从 MySQL 重建出一轮缓存；
4. 后续请求一直命中这一份旧缓存。

### 10.4 修复

将缓存追加移动到数据库 `try / except` 之外：

```python
try:
    # 保存 MySQL
    ...
except Exception as e:
    raise StageError("DB", e)

if context_turns &gt; 0:
    # MySQL 成功后追加 Redis
    ...
```

修复后每轮日志同时出现：

```text
[DB] 本轮对话已保存
[Redis] 本轮对话已追加到缓存
```

### 10.5 为什么旧测试假通过

旧测试只运行两轮：

- 第一轮历史为 0；
- 第二轮即使 Redis 追加失败，也能从 MySQL 读到第一轮；
- 因此测试会通过。

只有第三轮及以后，才能暴露“缓存一直停留在一轮”的问题。

这说明测试不仅要检查最终结果，还要设计能区分不同实现路径的用例。

### 10.6 新增四轮回归测试

新的 `test_pipeline_context.py`：

- 模拟 ASR、LLM 和 TTS；
- 连续运行四轮；
- 检查传入 LLM 的历史依次为 0、1、2、3 轮；
- 检查第三轮和第四轮携带完整历史；
- 检查四轮 MySQL 记录；
- 直接读取 Redis，确认缓存也累积四轮；
- 自动清理数据库、缓存和模拟音频。

直接检查 Redis 是为了防止 Pipeline 通过 MySQL 回退掩盖缓存追加故障。

## 14. 当前限制

- 本地单用户，无登录和权限控制。
- 管理接口不应直接暴露到公网。
- 重连后创建新会话，不自动恢复旧会话。
- 只有最近 10 轮进入 LLM。
- LLM 使用历史仍具有概率性，不能用一次回答代替数据层测试。
- 情绪固定为 `neutral`。
- 使用 `create_all` 初始化，尚无正式数据库迁移。
- Edge TTS 依赖外部网络。
- Demo 视频暂不阻塞版本验收。

## 15. 后续计划

### v0.3 优先：会话恢复

考虑让客户端保存并回传稳定的会话标识，或者引入独立 `conversation_id`：

1. 重连时请求继续最近会话；
2. 服务端从 MySQL 恢复最近 N 轮；
3. 自动重建 Redis；
4. 未携带标识时仍创建新会话；
5. 保持旧客户端兼容。

之后再逐步加入情绪驱动的角色表现。

### 更后续：长期记忆

长期记忆不是简单增加 `context_turns`，而是需要从完整历史中选择与当前问题相关的内容，同时控制 Token、延迟、冲突和过期信息。

## 16. 版本总结

v0.2 完成了从“单次语音问答”到“具有数据持久化、短期多轮上下文和管理后台”的升级。

本版本最重要的工程经验是：

&gt; 模型某次回答正确，不能证明上下文链路正确；模型某次回答错误，也不能直接证明缓存失效。必须结合日志、数据库、缓存内容和自动化测试逐层验证。

Redis 缩进 Bug 也说明了回归测试需要覆盖第三轮及以后，并直接验证关键副作用，而不能只检查系统表面上“还能回答”。
