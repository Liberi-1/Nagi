# Nagi v0.1 开发日志

&gt; 状态：已完成。A/B/C 及异常测试均已完成；Demo 暂缓，待角色模型与声音方案确定后补充。
&gt; 记录日期：2026-11-22

## 本版本目标

语音对话数字人最小闭环：Unity 麦克风录音 → 后端 ASR → LLM → TTS → Unity 播放回复音频，角色同步切换 Talking/Idle 动画。

## 当前进展

- A 部分：完成四个模块（asr.py / llm.py / tts.py / pipeline.py），命令行实现"音频进、音频出"。
  端到端耗时约 7.3 秒（CPU Whisper base + DeepSeek API + Edge TTS）。
- B 部分：完成 WebSocket 服务。Echo 验证 → 自定义消息协议（docs/protocol.md）→ 接入 Pipeline →
  异常处理（分层错误码、60 秒超时、网络错误有限重试）。以 Python 测试客户端模拟 Unity 完成验证。
- C 部分：完成 Unity 客户端。Animator 状态机、麦克风录音与 WAV 导出、C# WebSocket 客户端、
  MP3 加载播放及 Talking/Idle 自动切换均已跑通，支持连续多轮对话。
- D 部分：完成空录音、静音、无效音频、后端离线与连续多轮测试；清理 Unity 与后端生成文件，
  完善开源文档。待录制 Demo 并发布 tag。

## 一、Bug 与解决

1. **ModuleNotFoundError: whisper（主力机）**
   现象：已安装却报缺包。定位：`sys.executable` 显示跑在系统 Python 3.11，venv 未激活。
   修复：激活 venv，并统一用 `python -m pip install` 保证安装与运行是同一解释器。

2. **requirements.txt 被污染**
   现象：新机器按清单装依赖失败。定位：清单混入 paddleocr、modelscope 等课程环境的包，
   系 freeze 时环境不洁所致。修复：手写最小依赖清单，只列直接依赖，传递依赖交给 pip 解析。

3. **pip 提示找不到 openai-whisper**
   原因：误用 `--index-url` 覆盖了 PyPI 源，导致只在 PyTorch 源中查找。
   修复：混合安装使用 `--extra-index-url`；torch CPU 版单独走 PyTorch 专用源。

4. **Whisper 报 WinError 2（系统找不到指定的文件）**
   原因：Whisper 解码音频依赖系统 FFmpeg，新机器未安装。
   修复：`winget install Gyan.FFmpeg`，重开终端刷新 PATH。

5. **重开终端后再次报 ModuleNotFoundError**
   原因：新窗口未重新激活 venv。修复：形成"开终端先激活"的习惯；
   VS Code 中选定项目解释器可自动激活。

6. **第二台设备缺少新模块文件**
   原因：主力机提交后未 push，且存在分支不一致风险。
   修复：建立"做完 commit + push、换机先 pull"的节奏，两台机器保持同一分支。

7. **英文专名被音译（Nagi → 奈迪）**
   原因：`language="zh"` 锁定中文输出，英文单词按发音音译为汉字；
   测试音频本身也是中文音色 TTS 合成的。判定：不影响 LLM 理解，记为已知限制，
   留待 v0.5 优化（可尝试 `initial_prompt` 引导）。

8. **TTS 报 Cannot connect to host speech.platform.bing.com**
   定位：网络层问题，非代码问题（同代码在另一台设备正常）。
   处理：重试 / 更换网络 / 检查代理。由此在第 8 步为 LLM、TTS 加入有限重试。

9. **pipeline 接入 async 服务的两个隐患**
   同步 pipeline 会阻塞事件循环；且 tts 中 `asyncio.run()` 不能在运行中的事件循环内调用。
   修复：以 `asyncio.to_thread` 将管线放入线程执行，一并解决两个问题。

10. **修改服务端代码后行为未变化**
    原因：服务进程未重启，仍运行旧代码。修复：重启进程；
    形成"改服务端代码必须重启"的习惯。

11. **Unity 启动报 License error**
    原因：直接安装独立编辑器，未通过 Unity Hub 登录并激活许可证。
    修复：安装 Unity Hub，登录后激活免费 Personal 许可证，再通过 Locate 添加已有编辑器。

12. **Unity 的 Library、Temp、UserSettings 出现在待提交列表**
    原因：Unity 工程位于仓库子目录，原有规则未覆盖该层级。
    修复：使用 `client-unity/` 前缀显式忽略生成目录；
    `Assets/`、`Packages/`、`ProjectSettings/` 和 `.meta` 文件正常入库。

13. **C# 打包请求后服务端无法解析长度**
    原因：协议规定 4 字节大端长度前缀，而 Windows/x86 的 `BitConverter` 默认小端。
    修复：发送前检查本机字节序，并在小端机器上执行 `Array.Reverse`。

14. **Unity 收到的 MP3 数据不完整**
    原因：WebSocket 的一条消息可能通过多次 `ReceiveAsync` 才能接收完，
    首次接收的缓冲区不一定包含完整音频。
    修复：循环接收并累积数据，直到 `EndOfMessage` 后再解析 JSON 头与音频负载。

15. **测试录音和运行产物混入版本库**
    现象：`backend/temp/` 下的临时 WAV、回复 MP3 和手动测试录音出现在 Git 变更中。
    修复：统一加入 `.gitignore`；已跟踪文件使用 `git rm --cached` 移出跟踪但保留本地文件。

16. **换机器后 Unity 资源引用可能丢失**
    原因：Unity 按 `.meta` 中的 GUID 引用资源，而非仅按文件名。
    修复：提交所有必要的 `.meta`；Mixamo FBX 因授权原因不入库，但保留对应 `.meta`，
    使用者按文档下载同名资源后即可自动恢复引用。

## 二、异常与恢复性测试

| 场景 | 结果 | 实际表现 |
|---|---|---|
| 空录音 | 通过 | ASR 阶段拦截空识别，返回明确错误，角色不卡在 Talking |
| 静音 / 纯噪音 | 通过 | 服务正常处理，未出现崩溃；识别准确性留待后续优化 |
| 无效音频文件 | 通过 | 返回 `ASR_FAILED`，FFmpeg 拒绝解析，服务进程保持运行 |
| 后端离线 | 通过 | 客户端出现明确连接错误日志；v0.1 需重新运行场景恢复连接 |
| 连续三轮对话 | 通过 | 每轮均能录音、接收回复、播放语音，并正确切换 Talking/Idle |

结论：v0.1 不追求所有异常都能自动恢复，但保证错误可识别、服务不崩溃、
正常流程可在明确操作后继续。断线自动重连留到后续工程化版本。

## 四、技术选型理由

- **为什么 WebSocket 而不是 HTTP**：长连接支持双向通信，适合"录音上传 → 异步处理 →
  主动推回结果"的实时对话场景，避免反复建立连接。
- **为什么先 API 后本地模型**：先用 DeepSeek / Edge TTS 跑通闭环，避免早期被 GPU、
  显存与部署复杂度拖住；本地模型留到 v0.5 配合机器学习课程进行。
- **为什么 Whisper 先用 CPU + base**：单点验证只求功能正确，不求精度与速度；
  GPU 加速不是本阶段的必要条件。
- **为什么协议是"4 字节头长度 + JSON 头 + 二进制音频"**：长度前缀让接收方精确分隔
  元数据与音频；JSON 可读性好、Python 与 C# 都有成熟序列化支持；大端序是网络传输惯例。
- **为什么人设外置 persona.md**：开源项目要求用户可自定义角色；配置文件保存即生效，
  调试人设无需重启；v0.2 可平滑升级为数据库 + Web 表单。
- **为什么先用 Mixamo 而不是原创建模**：美术不阻塞主线；且 Mixamo 素材不宜随开源仓库
  分发，仓库仅提供下载指引，原创角色由 Blender 支线最后完成。
- **为什么手写最小 requirements.txt 而非直接 pip freeze**：freeze 会钉死全部传递依赖并
  可能带入环境污染，跨机器安装脆弱；只列直接依赖最稳。
- **为什么使用 .NET 内置 ClientWebSocket**：已经满足文本与二进制帧收发需求，
  无需为最小闭环增加第三方包，也减少 Unity 跨平台依赖问题。
- **为什么录音先转为 16 位 PCM WAV**：格式简单、后端解码稳定，
  且便于直接复用 FFmpeg 与 Whisper 的已有处理流程。
- **为什么用 Animator 布尔参数控制动画**：Idle/Talking 只有两个状态，
  `IsTalking` 足以表达切换逻辑；相比直接播放动画，后续增加表情和动作状态时更易扩展。

## v0.1 总结

本版本完成了从语音输入到角色回应的完整最小闭环，并验证了双机开发、
开源资源配置和常见异常场景。当前重点不是画面或模型能力的完整度，
而是建立一个可运行、可复现、可继续迭代的端到端骨架。

v0.2 将在此基础上加入数据层和 Web 管理后台，支持网页配置人设、
保存对话记录，并引入多轮上下文。
